AYA

A second AI that reads AI-written code and says "looks good" asks to be believed. AYA does not ask that. It runs the code before and after the change, lets the old code be the judge, and tells the person who signs where to look and why. No black box decides anything: every line of a report can be opened and run again.

The problem

A verdict is not something a person can sign under

An agent writes a thousand lines in minutes. A person still approves them. The common answer is a second model that reviews the first.

A reviewing model gives a verdict

"I would not approve this." It may be right. But it changes from one run to the next, its silence about a file means nothing, and the person has no way to weigh it except by trusting the model.

AYA gives evidence, in order

"This input compiled before the change and does not now." "No test needs these four lines." "2,542 inputs give the same result, and they run every changed line." Each can be re-run by anyone.

Trust is earned by the measurement, not by the model that proposes it.

No black boxes

Nothing in a report has to be taken on trust

A language model is a black box: it cannot show why it said what it said. AYA uses models, and is built so that no black box ever decides anything. Every line of a report can be opened.

Every number opens

Each figure in the report comes from evidence.json, and the report names that file by its hash. Change a number and the hash no longer matches.

Every finding runs

Behind each place in the list there is a file: the test, the input, the result on the old code and on the new. Anyone can run it again and get the same answer.

The order is a rule, not a score

Six tiers, written in one sentence each and printed in every report. No weights, no learned ranking, nothing to tune. The owner can read why an item is third and disagree.

What a model touched says so

Code a model wrote is saved next to the report, exactly as it was built and run. What a model believes is marked as an opinion, with the words it rests on checked against the requirement.

Where a black box remains, we say where: the harness that feeds inputs to the sweep is written by a model and accepted for how it behaves (it runs on both versions, repeats on the old code, executes the change), not because someone read it. Replacing it with a fixed one is on the list.

What is new in this architecture

Seven ideas, each with a result behind it

1

The old code is the arbiter

Every check runs twice: on the code before the change and on the code after. A test written by a model that fails on the new code is worth nothing until it is run on the old. If it fails there too, the change is not the cause and the test is dropped.

Fifteen sets of model-written tests that looked like findings failed on the old code too, and were discarded on evidence, not on judgement.

2

Three kinds of contribution, one rule

What AYA measures. What a model writes, which AYA builds and runs. What a model believes, which is shown as a belief. The rule that separates them: a model may lower trust on its opinion, and raise it only through something that was measured. A model's reading can move an item up the list, never down.

3

An input layer: brute force without a model

The best finding of the first day existed because a model happened to think of one input. So inputs are now built by rule, between the tests and the sweep:

Where they come from
  • sources the existing tests hold
  • analyzer-test sources with their marks removed
  • sources that came with the change
➜
How they are altered
  • from the change: put on every type the attribute it emits; define the symbol it tests
  • a family of 34, by scheme over C# syntax: take one thing out, swap for another of its kind, alter a literal, move a type to another library, wrap a member's type
➜
What is observed
  • diagnostics and generated code
  • does the tool crash?
  • does its output compile?
  • what happened to the user's own types?

On one change the sweep went from "300 inputs, no difference" to 49 differences in 2,542 inputs, among them generated code that no longer compiles. No model chose any of those inputs.

4

The change showing through

A change that alters every output produces hundreds of differences, and the one that matters hides among them. A difference made only of lines the change itself adds or removes is recognised without a model and set aside.

All differences between old and new code1,860
minus those made only of the change's own lines1,811 set aside, no model
the judge reads what is left46, as an opinion
what stopped working goes first, whatever anyone thinks3
5

Undo the change, one part at a time

Put the old lines of one part back and run the tests. If they all pass, no test needs that part: nothing shows what it is for. This is how a change that does more than was asked becomes visible.

On one fix, the new filter turned out to be needed by exactly one test, and that test came with the change. An independent reviewer reached the same conclusion by hand.

6

Memory: a finding does not depend on luck twice

What a model writes varies. The same stage found a regression one day and missed it the next. So a test that showed a regression is kept and arbitrated again on every later review of the branch.

On one branch the fresh attack found nothing in the last pass. The test kept from the first review still put the regression in first place.

7

Opinions with their feet on the ground

A judge says whether a difference was meant, and reads the requirement against the tests. Two things in every reading are checked by AYA: the words it quotes must be in the requirement, and a test it names must be one that really fails on the old code. A reading that fails either check is discarded.

One reading of "this was meant" quoted words that were not in the change. AYA threw it out.

What the owner receives

One screen to decide, and everything behind it

The order is a fixed rule, printed in every report, so the owner can disagree with it. Risk is never one score: likelihood, impact, detection and what the analysis cannot see are shown apart.

1A check that passed on the old code fails on the new

What Tieto asked to see, and where it is

What the AI found. The ordered list, with the measurement behind each place.

What it refused to decide. Whether a difference was meant; whether the requirement is met. Shown as a model's reading, never as a result.

What it did not check. A section of every report: documentation, deleted code, lines no input reaches.

A named human stays accountable. Every report ends with a sign-off block: how far down the list the owner looked, and the residual risk they accept.

Built the way it asks others to be

What went wrong, and what it became

It said things could be skipped

An early version reported "14 of 228 lines left to read". An outside audit showed the figure was wrong on two of four changes. AYA now orders and never excludes.

A model gamed the check

Asked for a test that catches an unobservable break, a model built an impossible object by reflection. Such tests are now refused.

Our labels said more than we measured

Ten cases, all confirmed in the code. Each became a test of AYA itself: 74 today, one for every way it was found to overstate.

How it scales

In a pipeline

It is a command line with an exit code. One review per pull request, each in its own working folder; four ran in parallel on one laptop.

Over time

Kept tests accumulate. Every regression ever demonstrated on a branch becomes a permanent check, written once and paid for once.

With any reviewer

Human or model, a reviewer hands a test to the arbiter and gets back a fact. AYA makes other tools' claims checkable instead of competing with them.
